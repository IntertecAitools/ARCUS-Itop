# Performance at production volume

What the platform does with a realistic amount of data, what was slow or wrong, what was fixed, and how big the production server should be. Measured on 2026-10-21 (branch `claude/data-volume-601f54`).

## Summary

With 50,000 tickets, 10,000 CIs, 2,000 people and 500 accounts, every screen answers in under half a second, except these:

- the dashboard: 1.1 s for 7 days, 2.3 s for 90 days;
- the audit runs: about 1 s;
- exports: 4–5 s for 10,000 rows, 17 s for 50,000;
- imports: 3 s to check 1,000 rows, 34 s to load 1,000 people.

That is after the fixes in this branch. Before them, three kinds of problem showed at this volume:

- **Wrong answers.** These were worse than the slowness:
  - the 90-day dashboard counted 6,132 incidents but drew a trend of 2,000;
  - "Recent incidents" showed tickets from a year ago;
  - the bell and "notifications sent" listed the oldest items instead of the newest.
- **Slow screens:**
  - the portal took 3–15 s for a user with many requests;
  - the dashboard took 4–10 s;
  - a sorted list of a big class took up to 11 s, only to be refused.
- **Silent truncation:**
  - the incident form offered only the first 200 people as agents;
  - dashlets counted the first 5,000 rows as if they were all;
  - exports and imports past 2 minutes failed while iTop kept writing.

What remains is iTop's own cost per call and its single-threaded bulk loader:

- every call costs a fixed ~0.1–0.4 s, mostly the password check;
- the bulk loader handles one row at a time.

See "Limits" and "Sizing".

### How long loading took

The data went in through REST, 6 calls in parallel, on the shared laptop. The other projects took 3–5 cores most of the time:

| Step | Records | Time | Rate |
| --- | ---: | ---: | ---: |
| iTop install (`itop-setup`) | | 14.5 min | |
| Organisations, people, teams, service catalogue, contracts | 2,446 | 14.7 min | 2.8/s |
| CIs | 10,000 | 42 min | 4.0/s |
| Accounts | 501 | 3.6 min | 2.3/s |
| Tickets | 50,000 | 3 h 49 min | 3.6/s (2.3/s busy, 4.5/s quiet) |
| Bell | 300 | 13 s | 23/s |
| **Total** | **~63,000** | **≈ 4 h 50 min** | |

A ticket is the expensive record. To create one, iTop runs about 110 SQL queries:

- trigger checks;
- CI impact;
- the ticket number;
- history.

Each REST call also checks the bcrypt password, which takes 70 ms on a free core and 370 ms on this loaded laptop. More than 6 calls in parallel did not help: the machine was CPU-bound.

MySQL settings during the load only:

- `innodb_flush_log_at_trx_commit=2` and `sync_binlog=0`. The ticket counter commits on its own, and each commit took ~0.5 s on this Docker disk.
- Every timing below was taken with the production values (1 and 1).

## What was slow or wrong, and the fixes

iTop's REST API returns rows in the **class's default order** and cannot be told otherwise. That default differs by class:

| Classes | Default order |
| --- | --- |
| `UserRequest`, `Incident`, `Problem`, `Change`, every event (the bell, sent emails) | **Newest first** (`ref` / `date` descending) |
| `Ticket` itself and most other classes | Ascending, by name |

Several screens assumed "oldest first, newest on the last page". With a handful of records everything fits on one page, which hid it.

| # | Problem at volume | Fix | Test |
| --- | --- | --- | --- |
| 1 | Dashboard, 90 days: the trend, category split and SLA came from the first 2,000 of 6,132 incidents | Reads the whole window (up to 20,000) in pages of 2,000, 4 at a time, with only the fields it needs | `volume.test.ts` |
| 2 | Same screen, 20 s once fixed: iTop computes the SLA-passed flags per row (~3 ms each) | The SLA split comes from two filtered counts in iTop instead of per-row flags | `volume.test.ts` |
| 3 | The BFF spent 1.3 s per 2,000 rows building a new `Intl.DateTimeFormat` for every date | One formatter per time zone (`shared/itop-time.ts`); every list, case log and history benefits | existing time tests |
| 4 | The "total incidents" KPI and the SLA split covered one day more than the trend | All three use the same window | `itop-time-paths.test.ts` |
| 5 | "Recent incidents" showed the oldest incidents; the bell and "notifications sent" showed the oldest items | `newestRows()` reads page 1 and, past one page, the end of the set, then keeps the highest ids, whatever the class order | `volume.test.ts` |
| 6 | Portal: up to 5 sequential calls of 100 rows that kept the oldest 500, so a busy user's newest requests never appeared | A count, then only the requested page, read from the end (`pageFromEnd()`): 2 calls at any volume | `portal.test.ts` |
| 7 | Grouping dashlets read up to 5,000 rows in sequence and reported 5,000 as the total | Enum and class groupings are counted per value by iTop (exact, a handful of calls). Open-ended ones (agent, organisation) are still scanned, now in parallel, with the real total and a "grouped from the first N" note | `dashboards.test.ts`, `Dashlet.test.tsx` |
| 8 | `listAll` read pages one after another and always asked for 500 rows, even to show 4 | Page size matched to the cap; the pages after the first go 4 at a time | `volume.test.ts` |
| 9 | A sorted list over 2,000 rows downloaded 2,000 rows before refusing | A one-row count first | `volume.test.ts` |
| 10 | Audit runs downloaded the category's whole set and each rule's whole result to compare them | iTop counts `set AND id [NOT] IN (rule)` per rule and lists the first 500 failing records; one OR'd count gives the overall figure. The old comparison remains for a rule over an unrelated class | `audit.test.ts` |
| 11 | Incident forms offered only the first 200 people as agents, out of 2,000 | Agents are team members (the only people iTop accepts), up to 2,000; organisations, teams and services up to 1,000 | `incidents.test.ts` |
| 12 | Exports and imports were cut off at 120 s (BFF and nginx), and iTop went on importing after the error | Those two routes get 300 s in the BFF and nginx (PHP's own `max_execution_time`). Imports refuse files over 1,000 tickets or 5,000 other rows at the preview step | `transfer.test.ts`; `nginx -t` |

Checked and fine at this volume:

- record lists: first and last page, filters, search, advanced search;
- record detail and history;
- nav counts;
- pickers (type-ahead, at most 500);
- notification rules;
- the bell's unread count;
- the portal catalogue.

Also checked, and left as they are:

- The CSV export's in-memory rewrite: 50,000 rows kept the BFF under 250 MB.
- My Assignments: its queues come from concrete classes, so they are newest first already.

## Limits that are iTop's own

### Every REST call costs ~0.1–0.4 s, whatever it asks for

On every call, iTop boots and checks the bcrypt password:

- `rest.php` resets the session each time;
- the hash cost is not configurable.

Screens are built to need few calls, and the remaining ones run in parallel. Mitigation: give iTop CPU cores (see "Sizing") and keep screens to a handful of calls.

### No server-side sorting

OQL has no ORDER BY, and `core/get` takes none. The BFF sorts in memory up to 2,000 rows and refuses past that. The list UI never sends a sort today; a sort sent through the URL on a big class gets the 400 at once.

Mitigation: filter first, with views, filters or search, which every list offers.

### The bulk loader is single-threaded

- It loads ~7.5 tickets/s and ~30 people/s on a free core, and far fewer on a busy one.
- One ticket created through REST runs ~110 SQL queries.

Mitigation: files of at most 1,000 tickets, which the BFF now enforces. Load an initial migration in the background, as `perf-seed.mjs` does.

### Exports run inside one request

50,000 tickets took 17 s on a quiet machine and would take ~2 min on a loaded one. The ceiling is PHP's `max_execution_time` of 300 s.

Mitigation: past ~100,000 rows, export filtered parts.

### Smaller caps

- **Grouping by an open-ended attribute** (by agent, by organisation) reads up to 5,000 rows. Past that, the dashlet says "grouped from the first N".
- **The change calendar** lists at most 50 changes for the week. This data has ~190 changes a week, so it shows the first 50.

### MySQL was never the bottleneck

- Across all runs, only ~55 queries took more than 0.5 s. The worst took 2 s, and all were large scans or exports.
- At 50,000 tickets the database is ~200 MB.
- No extra indexes are needed: iTop indexes every external key (caller, agent, team, organisation).
- Past a few hundred thousand tickets, an index on `ticket.start_date` (the dashboard's window) would be the first to add.

### Ticket numbering is a global lock with its own commit

On a slow disk it serialises every ticket create; each commit took 0.5 s here. Production MySQL needs a disk with fast fsync: SSD, not network storage.

## Sizing the production server

For ~500 staff and portal users, with tens of thousands of tickets a year:

| Part | Recommendation | Why |
| --- | --- | --- |
| Server | **4 vCPU, 8 GB RAM, SSD**, one VM for the whole stack | iTop is CPU-bound: one REST call is ~0.1 s of CPU on a free core, and a screen makes 4–6 calls in parallel, which should not queue. 2 vCPU is the floor for a pilot. |
| iTop (PHP) | The image's defaults: opcache 256 MB, APCu, `memory_limit` 512M, `max_execution_time` 300 | Measured: opcache used 45 MB with a 99.7% hit rate, and was never full |
| MySQL | `innodb_buffer_pool_size` = **1 GB** (the default is 128 MB); keep `innodb_flush_log_at_trx_commit=1` | ~200 MB of data at 50,000 tickets, growing ~4 MB per 1,000 tickets with their history. The whole database should stay in memory |
| BFF | 1 instance, ~300 MB | Peaked at 250–340 MB during a 50,000-row export (dev mode) |
| Disk | 20 GB to start, plus backups (~10 MB of dumps a day at this size) | |

In `docker/docker-compose.prod.yml` the bundled MySQL runs with its defaults. For the buffer pool, add `--innodb-buffer-pool-size=1G` to `db.command` once the server has the memory. With 8 GB, iTop, MySQL, the BFF and nginx fit with room to spare.

If screens slow down under real use, watch iTop's CPU first, and add cores before anything else.

## Reproducing

```bash
# 1. A separate iTop: the prod stack as its own project, on a free port (see docs/deployment.md).
#    Test env files outside the repo; ITOP_ADMIN_PORT=8189 publishes iTop for the BFF.
docker compose -p arcus-perf -f docker/docker-compose.prod.yml -f docker/docker-compose.prod.itop-admin.yml \
  --env-file <perf prod.env> up -d --no-build db itop
docker compose -p arcus-perf ... exec -u www-data itop itop-setup

# 2. Data (hours; see above). Set the iTop account, and a password for every perf.* account.
cd backend
PERF_ITOP_URL=http://127.0.0.1:8189 PERF_ITOP_USER=... PERF_ITOP_PASSWORD=... PERF_USER_PASSWORD=... \
  node scripts/perf-seed.mjs --concurrency 6 --until 2026-10-21

# 3. A BFF on that iTop (backend/.env: ITOP_BASE_URL=http://127.0.0.1:8189, PORT=4800), then:
PERF_PASSWORD=... node scripts/perf-measure.mjs http://127.0.0.1:4800 --runs 3

# 4. Remove it all.
docker compose -p arcus-perf ... down -v
```

`perf-seed.mjs` refuses `:8080` (the shared local iTop). Never point it at an iTop people use.
