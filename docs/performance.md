# Data-volume check: report, 2026-10-21

This report covers how the platform behaves with production-sized data, measured before going live:

- how fast every screen answers;
- what was slow or gave wrong answers, and what was fixed;
- what remains slow because of iTop itself;
- how big the production server should be.

The check ran on 2026-10-21, on branch `claude/data-volume-601f54` (PR #21).

Raw numbers, one row per call, set and BFF: [`performance-data/2026-10-21.csv`](performance-data/2026-10-21.csv). See "Data files" at the end.

## 3. How it was measured

`backend/scripts/perf-measure.mjs` signs in as `perf.admin` (staff) and `perf.user001` (portal), then calls the BFF the way the screens do:

- **3 runs** per call, one after the other, on a warm BFF;
- median and worst reported. With 3 runs the 95th percentile equals the worst, so no separate p95 is given. The script prints p95 and saves every run with `--csv` for later checks.

The time is what the browser waits for that one call. A screen makes one or a few of them in parallel. Before and after ran back to back on the same data.

The import of 1,000 rows is a simulation (nothing written), except where marked "real".

The export case uses the oldest user requests up to the day that makes ~10,000 (10,014 at 50,000 tickets; 4,897 at the checkpoint, when that was all of them).

## 5. What was wrong, the fixes, and what each gave

The root cause of most wrong answers: iTop's REST API returns rows in **each class's default order** and cannot be told otherwise.

| Classes | Default order |
| --- | --- |
| `UserRequest`, `Incident`, `Problem`, `Change` and every event (the bell, sent emails) | **Newest first** (`ref` or `date` descending) |
| `Ticket` itself and most other classes | Ascending, by name |

Several screens assumed "oldest first, newest on the last page". With a handful of records everything fits on one page, which hid it.

| # | Problem at volume | Fix | Commit | Gain (50k quiet; 12k busy in brackets) |
| --- | --- | --- | --- | --- |
| 1 | Dashboard: trend, category split and SLA built from the first 2,000 incidents of the window | Reads the whole window (up to 20,000) in 2,000-row pages, 4 at a time, with only the fields it needs | `804ad1d` | **Correct**: 90-day trend 6,078 of 6,078 (was 2,000 of 6,132). Alone it took 21.8 s; see 2 and 3 |
| 2 | iTop computes the SLA-passed flags per row (~3 ms each: a 2,000-row page took 6.9 s with them, 0.5 s without) | SLA split from two filtered counts in iTop | `cb3034f` | With 3: 90 days 21.8 s → 2.3 s |
| 3 | A new `Intl.DateTimeFormat` for every date: 1.3 s of BFF time per 2,000 rows | One formatter per time zone (`shared/itop-time.ts`) | `cb3034f` | Scanning 6,132 rows: 5.7–7.3 s → 1.9–3.1 s. Every list, case log and history gains |
| 4 | KPI and SLA split counted one day more than the trend | Same window for all three | `cb3034f` | KPI 861 → 764 = trend |

## 6. What stays slow, and iTop's own limits

| Limit | Measured | Mitigation |
| --- | --- | --- |
| **Fixed cost per REST call.** iTop boots and checks the bcrypt password on every call (`rest.php` resets the session; the hash cost is not configurable) | ~0.15 s per trivial call quiet, 0.5–0.8 s busy; bcrypt 368 ms CPU busy | CPU cores for iTop (section 7). The BFF keeps screens to a handful of parallel calls |
| **No server-side sorting.** OQL has no ORDER BY and `core/get` takes none | The BFF sorts up to 2,000 rows in memory and refuses past that (now in 0.19 s). The list UI never sends a sort today | Filter first: views, filters and search on every list |
| **Single-threaded bulk import** (`import.php`, one row at a time) | ~7.5 tickets/s, ~30 people/s quiet | Files of at most 1,000 tickets / 5,000 other rows (enforced). Load a migration in the background, as `perf-seed.mjs` does |
| **Exports run inside one request** | 50,000 tickets: 17 s quiet, ~2 min busy (projected) | 300 s budget; past ~100,000 rows, export filtered parts |
| **Portal and dashboard queries on the abstract `Ticket` class** | 0.6–1.3 s each in iTop (busy); the portal needs 2 | Acceptable at 0.3–0.45 s quiet; more cores |
| **Grouping by an open-ended attribute** (agent, organisation) | Reads up to 5,000 rows | The dashlet says "grouped from the first N" past that |
| **Change calendar** | At most 50 changes for the week; this data has ~190 a week | Not changed in this check |
| **Ticket numbering** is a global lock with its own commit | 0.5 s per commit on this Docker disk serialised every ticket create | Production MySQL on a disk with fast fsync (SSD, not network storage) |
| **MySQL** | Never the bottleneck. ~55 queries over 0.5 s across all runs (worst 2 s, all big scans or exports). Data ~200 MB at 50,000 tickets (the volume is 724 MB including binary logs from the load) | No extra indexes needed: iTop indexes every external key. Past a few hundred thousand tickets, an index on `ticket.start_date` would be the first to add. Binary logs: set `binlog_expire_logs_seconds` to match the backup schedule |

## 7. Production server sizing

For ~500 staff and portal users, with tens of thousands of tickets a year:

| Part | Recommendation | Why (measured) |
| --- | --- | --- |
| Server | **4 vCPU, 8 GB RAM, SSD**, one VM for the whole stack; 2 vCPU is the floor for a pilot | iTop is CPU-bound: ~0.1 s of CPU per REST call on a free core, and a screen makes 4–6 calls in parallel. The busy-laptop numbers (section 4.2) show what fewer free cores do |
| iTop (PHP) | The image's defaults: opcache 256 MB, APCu, `memory_limit` 512M, `max_execution_time` 300 | opcache used 45 MB, 99.7% hit rate, never full |
| MySQL | `innodb_buffer_pool_size` = **1 GB** (default 128 MB); keep `innodb_flush_log_at_trx_commit=1` | ~200 MB of data at 50,000 tickets, growing ~4 MB per 1,000 tickets with history; it should all stay in memory |
| BFF | 1 instance, ~300 MB | 246–337 MB during a 50,000-row export (dev mode) |
| Disk | 20 GB to start, plus backups (dumps ~10 MB a day at this size) and binary-log retention | |

In `docker/docker-compose.prod.yml` the bundled MySQL runs with defaults. Add `--innodb-buffer-pool-size=1G` to `db.command` once the server has the memory.

If screens slow down under real use, watch iTop's CPU first and add cores before anything else.

Not measured here:

- a Linux server;
- many users at once (each call was timed alone);
- iTop's cron and SLA targets: no SLTs were defined, so every SLA flag was zero;
- Excel and PDF exports of 50,000 rows.

## 8. Re-running the check

Allow ~6 h, mostly loading, and ~2 GB of free disk for Docker. The env files hold test passwords only; keep them outside the repository.

```bash

$DC up -d --no-build --wait db itop

# 1. Optional, load only: faster commits (restore 1 / 1 before measuring).

# 2. Data (≈ 5 h on the laptop above; idempotent, resume by running it again).

# 3. Two audit categories over all requests and all CIs (section 2), e.g. through iTop's REST
#    core/create: AuditCategory "Perf: user requests" (SELECT UserRequest) with rules
#    "SELECT UserRequest WHERE status = 'assigned' AND agent_id = 0" (lists faulty) and
#    "SELECT UserRequest WHERE status != 'closed' OR solution != ''" (lists valid); "Perf: CIs"
#    (SELECT FunctionalCI) with "SELECT FunctionalCI WHERE business_criticity = 'high'" (faulty).
#    perf-measure.mjs expects them as categories 1 and 2.

# 4. Back to production durability, then a BFF on that iTop:
#    backend/.env with ITOP_BASE_URL=http://127.0.0.1:8189, the ITOP_USER above, PORT=4800, SESSION_STORE=memory
docker exec arcus-perf-db-1 mysql -uroot -p<root> -e "SET GLOBAL innodb_flush_log_at_trx_commit=1; SET GLOBAL sync_binlog=1;"
node --import tsx src/index.ts &

# 5. Measure, and keep every run for comparison.
PERF_PASSWORD=<perf.* password> node scripts/perf-measure.mjs http://127.0.0.1:4800 --runs 10 \
  --label after --csv ../docs/performance-data/<date>-runs.csv

# 6. Remove it all (volumes included).
cd ../docker && $DC down -v
```

To compare with an older version, run a second BFF from that commit on another port (`git archive <commit> backend cmdb-schema | tar -x -C <dir>`, the same `.env` with another `PORT`) and measure it the same way.

## Data files

`docs/performance-data/2026-10-21.csv` has one row per call, set and BFF: 131 rows. Columns:

| Column | Meaning |
| --- | --- |
| `date` | Date of the measurement |
| `set` | `checkpoint-12k`, `final-50k` (3 runs), or `final-50k-single` (one run: full exports, real imports) |
| `tickets` | Tickets in iTop at the time |
| `host_load` | `busy` or `quiet` laptop |
| `bff` | `before` or `after` |
| `commit` | The BFF's commit |
| `call` | The screen or call |
| `runs` | Number of runs |
| `median_ms` | Median time |
| `worst_ms` | Worst time |
| `result` | Rows or size returned |

This check recorded median and worst only. From now on, `perf-measure.mjs --csv` saves every run (`date,bff,call,run,status,ms,bytes`), from which a later check can compute p95.
