## Setup

| | |
| --- | --- |
| iTop | The production stack (`docker/docker-compose.prod.yml` + `docker-compose.prod.itop-admin.yml`), as its own compose project `arcus-perf`: iTop 3.4 (image `arcus-itop`), MySQL 8.4 in Docker (database `itop_perf`, defaults: 128 MB buffer pool), installed with `itop-setup`. iTop on `127.0.0.1:8189`. No cron (nothing it does was measured). The shared local iTop (`itop-local`, `itop_prod`) was not touched. |
| BFF | Two, both from `backend/` with an `.env` aimed at that iTop, memory sessions: **after** = this branch on `:4800`, **before** = `main` at `05a3c24` on `:4801`. Same data, same iTop, measured one after the other. |
| Frontend | Vite dev server on `:5873` against the BFF on `:4800`, for the in-browser check. |
| Machine | One Windows 11 laptop, 8 cores; Docker Desktop VM with 8 CPUs and 7.7 GB. **Shared**: other projects' containers used 3–5 cores throughout, so absolute times are pessimistic. Compare *before* and *after*, and see "Sizing" for a dedicated server. |

### Data

Generated by `backend/scripts/perf-seed.mjs`, entirely through iTop's REST API (`core/create`), seeded (`--seed 42`) and idempotent: every record has a deterministic key, so a rerun creates only what is missing.

| What | Count | Notes |
| --- | ---: | --- |
| Organisations | 20 | 1 IT provider + 19 customers |
| People | 2,000 | 600 at the provider (agents), 1,400 across the customers |
| Teams | 100 | 6 agents each |
| Services and subcategories | 300 | 6 families, 60 services, 240 subcategories (incident / service request); every customer has a contract for every service |
| CIs | 10,000 | PCs, servers, network devices, printers, phones, application solutions |
| Accounts | 501 | `perf.admin` (Administrator), 300 Support Agents, 200 portal users |
| Tickets | 50,000 | 20,000 user requests, 18,000 incidents, 2,000 problems, 9,000 changes (normal, routine, emergency) |
| Bell | 300 | Newsroom notifications for `perf.admin` |

Tickets are spread over the 12 months before 2026-10-21, slightly more of them recently. Each is filed after the one before (refs follow time, as in real use). Older tickets are mostly closed; recent ones are new, assigned, pending or resolved. Each has a team and agent once assigned, a service and subcategory, 1–4 public case-log entries (private for problems and changes), and 60% of incidents and requests have a CI. `perf.user001` is the caller of ~1,500 requests (the portal case).

## Reproducing

```bash
# 1. A separate iTop: the prod stack as its own project, on a free port (see docs/deployment.md).
#    Test env files outside the repo; ITOP_ADMIN_PORT=8189 publishes iTop for the BFF.
docker compose -p arcus-perf -f docker/docker-compose.prod.yml -f docker/docker-compose.prod.itop-admin.yml \
  --env-file <perf prod.env> up -d --no-build db itop
docker compose -p arcus-perf ... exec -u www-data itop itop-setup

# 2. Data (hours; see above). Set the iTop account, and a password for every perf.* account.
cd backend
PERF_ITOP_URL=http://127.0.0.1:8189 PERF_ITOP_USER=... PERF_ITOP_PASSWORD=... PERF_USER_PASSWORD=... \
  node scripts/perf-seed.mjs --concurrency 6 --until 2026-10-21

# 3. A BFF on that iTop (backend/.env: ITOP_BASE_URL=http://127.0.0.1:8189, PORT=4800), then:
PERF_PASSWORD=... node scripts/perf-measure.mjs http://127.0.0.1:4800 --runs 3

# 4. Remove it all.
docker compose -p arcus-perf ... down -v
```

`perf-seed.mjs` refuses `:8080` (the shared local iTop). Never point it at an iTop people use.
